# Metatron Lab 2.0 — аудит перед реализацией

Дата: 23.11.2026. Основа: ветка `main`, версия `1.5.0-rc.63`. Сценарий владельца: `docs/product/METATRON_LAB_2_SCENARIO.pdf`.

Это этап 1 из сценария («сначала анализ, затем изменения»). Код не менялся, ничего не удалялось. Файлы читались по именам, заголовкам и публичным символам; построчная проверка каждого модуля не делалась, такие места помечены «не проверено».

## Главный вывод

Почти все компоненты сценария уже есть. Второй оркестратор, второй движок исполнения или второй Context Engine создавать нельзя. Метатрон выглядит пустым по двум причинам:

1. Обычный чат (`answer-agent`) идёт мимо миссий, поэтому пульту нечего показывать. В боевой D1 за всё время 7 миссий и 0 запросов подтверждения (запрос к таблицам `missions`, `approval_requests` от 23.11.2026).
2. Граф миссии показывается как `derived-linear` (простая цепочка), потому что планировщик не сохраняет зависимости между шагами.

## Чего не хватает

1. Статусы Waiting Approval и Blocked.
2. Явные зависимости шагов в планировщике.
3. Карточка подтверждения в чате вместо ручных переключателей в настройках.
4. Report Agent и итоговый отчёт.
5. Независимая проверка результата (Review Agent).
6. Изоляция изменений в отдельной ветке, просмотр diff, `open_pr` через подтверждение.
7. Browser Agent (нужен браузер: Cloudflare Browser Rendering или запуск через локального помощника на ПК владельца).

## План этапов

Один этап = один Pull Request. Слияние делает владелец.

| №   | Этап                               | Критерий завершения                                                                                                                                                               | Решение владельца                                |
| --- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| 1   | Аудит (этот документ)              | Документ в `main`, устаревшие утверждения исправлены                                                                                                                              | —                                                |
| 2   | Карточка подтверждения в чате      | Нужное разрешение запрашивается карточкой «один раз / на задачу / на сессию / отклонить», ручное включение локального агента не требуется; критические действия всегда спрашивают | —                                                |

## Правила работы

- Сначала анализ, потом изменения; крупных переписываний нет.
- Работающие маршруты, контракты, подтверждения, чекпоинты и восстановление сохраняются.
- Удаление только после доказательства, что компонент не нужен.
- Основная ветка защищена; слияние делает владелец.
- Staging не источник архитектурных решений.
